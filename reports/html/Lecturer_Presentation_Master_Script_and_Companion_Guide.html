SECTION 1: THE 4 COMPILER PHASES (WHERE AST IS BORN)

The foundation of our static analysis tool is built directly upon Compiler Theory. A computer's CPU is an electronic chip that only understands binary digits: 0 and 1 (Machine Code). A compiler serves as the official translator. When high-level code is compiled, it passes through 4 major phases:

Compiler Phase What it Does Internally Example on rsa.generate(2048) How Our Security Tool Hooks In
1. Lexical Analysis
(Pengecaman Token)		 Reads the raw string of characters left-to-right and breaks it into atomic tokens. ['rsa', '.', 'generate', '(', '2048', ')'] Used in our Java scanner (re) to tokenize JCA factory calls without spinning up a heavy JVM.
2. Syntax Analysis
(Membina AST)		 Enforces language grammar and constructs the hierarchical Abstract Syntax Tree (AST). Builds tree: Root ast.Module ➔ Branch ast.Assign ➔ Leaf ast.Call 🌟 OUR CORE INTERCEPTION POINT! We borrow the compiler's parsing brain to inspect code structure without executing it.
3. Semantic Analysis
(Analisis Makna)		 Validates logical consistency: variable declaration, type safety, and symbol table scope. Checks: Does the variable rsa exist in current scope? Our tool validates import aliases (self._import_aliases) to guarantee algorithm identity.
4. Code Generation
(Penjanaan Kod)		 Translates validated AST into binary machine code (0101...) or Bytecode (.pyc / .class). Emits CPU binary or Python VM bytecode. We prevent malicious/vulnerable code from reaching this stage by pausing execution via LangGraph interrupt()!

THE INVERTED AST TREE ANATOMY (WHY IS IT CALLED A TREE?)
🌳 Deconstructing: private_key = rsa.generate_private_key(key_size=2048)
In computer science, an Abstract Syntax Tree (AST) is an inverted tree. Unlike biological trees that grow upwards from the soil, a compiler tree grows downwards from a single Root at the top. Compilers do not treat code as plain text; they break code into a root container, branching statements, and leaf parameters:
[ROOT: ast.Module] (Top Level 0 — The Source File Container) │ └── [BRANCH: ast.FunctionDef(name='generate_rsa_keypair')] (Level 1 — Function Scope) │ └── [BRANCH: ast.Assign] (Level 2 — Variable Assignment Statement) ├── targets[0]: [LEAF: ast.Name(id='private_key')] (Left Leaf — Target Variable) │ └── value: [🎯 BRANCH: ast.Call] (Level 3 — INTERCEPTION POINT!) │ └── Our _PythonCryptoVisitor intercepts here! Matched in LEGACY_CRYPTO_DB["RSA"] │ ├── func: [SUB-BRANCH: ast.Attribute(value=ast.Name(id='rsa'), attr='generate_private_key')] │ └── Reconstructed via ast.unparse(node) back into "rsa.generate_private_key" │ └── keywords[0]: [LEAF: ast.Constant(value=2048, arg='key_size')] └── Exact integer value extracted: 2048 bits (Flags Deprecated RSA!)

SECTION 7: POST-QUANTUM CRYPTOGRAPHY IN DEPTH

To defend your project against rigorous academic questioning, you must understand the mathematical difference between classical cryptography and post-quantum lattice cryptography:

💥 Classical Cryptography (Broken by Quantum)
  • RSA (Rivest-Shamir-Adleman): Security relies on the hardness of Prime Integer Factorization.
  • ECDSA & Diffie-Hellman: Security relies on the Discrete Logarithm Problem over elliptic curves.
  • Shor's Quantum Algorithm (1994): Uses Quantum Fourier Transforms (QFT) to find function periodicity in $\mathcal{O}((\log N)^3)$ polynomial time. This breaks RSA-2048, RSA-4096, and all standard ECC curves (secp256r1).
  • Harvest Now, Decrypt Later (HNDL): Adversaries store intercepted ciphertext today to decrypt in 2030+.
🛡️ NIST Post-Quantum Standards (Quantum-Safe)
  • NIST FIPS 203: ML-KEM (Module-Lattice KEM): Formerly Kyber. Solves the Module Learning with Errors (M-LWE) problem in high-dimensional polynomial lattices. Shor's algorithm has no sub-exponential speedup.
  • NIST FIPS 204: ML-DSA (Module-Lattice DSA): Formerly Dilithium. Lattice-based digital signature scheme providing existential unforgeability under chosen message attacks (EUF-CMA).
  • IND-CCA2 Security: Guarantees indistinguishability against adaptive chosen-ciphertext attacks.

SECTION 8: ANTICIPATED LECTURER QUESTIONS & MODEL ANSWERS

During your viva / evaluation, academic panels deliberately ask probing questions to test whether you truly wrote the system or copied an online template. Here are the 7 most common difficult questions and their winning responses:

❓ Q1: "Why did you use AST for Python but a Regex Scanner for Java? Isn't that inconsistent?"
Winning Answer: "That was a deliberate engineering decision based on language architecture and runtime efficiency. In Python, code is highly dynamic—developers can alias modules (import RSA as my_rsa) or monkey-patch functions, which causes flat regex tools to fail. The CPython PEG Parser is natively built into Python's standard library, so AST parsing has zero external dependencies and zero setup cost.

However, for Java, parsing an AST requires spinning up a Java Virtual Machine (JVM) or utilizing Eclipse JDT / JavaParser, which consumes over 200MB of RAM and introduces seconds of compilation latency. Because enterprise Java cryptography strictly enforces standard factory singleton APIs under the Java Cryptography Architecture (JCA)—specifically KeyPairGenerator.getInstance("algorithm")—a regex scanner based on a Deterministic Finite Automaton (DFA) achieves 88.4% precision with sub-20ms latency. We chose the optimal tool for each runtime."
❓ Q2: "What happens if a developer puts 'RSA' inside a comment? Does your system flag it?"
Winning Answer: "In Python, no, it is never flagged! This is one of the greatest advantages of compiler-level AST over classical regex tools. During CPython's Phase 2 Syntax Analysis, the parser strips all comments and whitespace before constructing the AST. An AST only contains executable syntax nodes (such as FunctionDef, Assign, and Call). Because comments do not exist in the AST, our _PythonCryptoVisitor never encounters them, resulting in zero comment false positives. In Java, our regex scanner applies a pre-filter stripping block (/* ... */) and line (//) comments before pattern evaluation."
❓ Q3: "In your code, why do you call self.generic_visit(node) inside visitor methods?"
Winning Answer: "In the classic Gang of Four (GoF) Visitor Pattern, ast.NodeVisitor dispatches method calls based on the node class name (e.g., visit_Call for ast.Call). When you override a visitor method, Python executes your custom logic and stops. If you do not call self.generic_visit(node), the visitor will not traverse into that node's children! For instance, if an assignment has a function call nested inside a list comprehension, failing to call generic_visit() would cause the visitor to skip the inner call entirely. Calling self.generic_visit(node) ensures complete recursive traversal through all child expressions."
❓ Q4: "How does your LangGraph interrupt() gate ensure AI safety?"
Winning Answer: "Most autonomous agent frameworks suffer from the 'runaway execution' problem, where the LLM can self-commit code directly to disk. In our architecture, the agent has zero write access to the repository during scanning and investigation. In node_human_approval(), we invoke LangGraph's native interrupt(). This physically freezes the execution thread in server RAM. The thread state is saved in MemorySaver. The process is completely inert—it cannot write, branch, or execute. It can only be resumed when a human reviewer inspects the Monaco side-by-side diff on port 8000 and explicitly submits an authenticated Command(resume={'decision': 'approved'})."
❓ Q5: "How does your SHA-256 audit ledger prevent someone from tampering with past records?"
Winning Answer: "Our audit trail operates as a recursive Merkle hash chain in _compute_chain_hash(). We initialize a 64-character zero-string as the Genesis hash. Each audit entry is serialized into canonical JSON using json.dumps(entry, sort_keys=True), concatenated with the previous entry's hash, and hashed with SHA-256. Because cryptographic hashes possess the Avalanche Effect, altering even a single byte in an approved audit record alters its hash, which cascades into every subsequent block hash. During verification, re-computing the chain yields a mismatch against the stored integrity hash, immediately flagging 'TAMPER DETECTED'."
